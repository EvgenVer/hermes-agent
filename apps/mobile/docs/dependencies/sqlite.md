# SQLite snapshot and migration dependency

Checked on 2026-08-26. This review covers the local structured cache for
redacted snapshots, not a credential store or an offline source of truth.

## Registry and compatibility

| Item | Evidence |
| --- | --- |
| Package | [`expo-sqlite`](https://www.npmjs.com/package/expo-sqlite), official Expo SQLite module. |
| Version | Expo SDK 57 documentation recommends `~57.0.1`; select that range. |
| License/type | MIT; native runtime package with an Expo config/plugin integration. |
| Android | The SDK documentation describes persisted SQLite storage with no additional Android setup for the standard module. |
| Maintenance | Maintained as part of the official Expo SDK release line and installed through `npx expo install`. |

The primary API references are [Expo SQLite](https://docs.expo.dev/versions/latest/sdk/sqlite/)
and its migration/provider examples. The module exposes asynchronous open,
bound parameter execution, reads, prepared statements, transactions, and
`PRAGMA user_version` migration patterns.

## Approved data and migration shape

SQLite may hold only redacted, bounded data: connection metadata without
credentials, profile summaries, paged session summaries, capability snapshots,
notification inbox metadata, and non-sensitive sync cursors. It must not hold
bearer/refresh tokens, SecureStore values, raw authorization headers, secrets,
unredacted logs, skill contents with credentials, or full attachment bytes.

Each table needs an explicit migration version. The initial migration should
use `PRAGMA user_version`, run inside a transaction, and be idempotent for a
fresh database. Schema changes must be additive or migrated with a transaction;
a failed migration leaves the app in a safe “cache unavailable” state while
the server remains authoritative.

All user/server values must use bound parameters or prepared statements. Expo
documents that `execAsync` does not escape parameters; it is therefore limited
to static migration SQL and PRAGMA statements whose text is generated by the
app, never interpolated profile names, session IDs, event data, or attachment
metadata.

## Encryption limitation and decision boundary

The standard Expo SQLite database is not encrypted by default. Expo documents
SQLCipher as an option requiring native configuration and prebuild, but SQLCipher
is not selected for Stage 1 because the approved cache excludes secrets and
unredacted sensitive data. If the data classification later expands, that is a
new security/dependency decision requiring a plan update and native validation;
it must not be solved by quietly placing credentials in the existing database.

## Testing and failure behavior

- Unit tests cover migration idempotence, bounded row projection, redaction,
  pagination/cursor persistence, and reset/reopen behavior using a temporary
  database or a deterministic test adapter.
- Android smoke tests open the real database on API 31 and API 37, apply all
  migrations, insert a redacted snapshot, reopen it, and verify the sensitive
  fields were never persisted.
- Busy/locked, disk-full, corrupt-schema, and migration errors are surfaced as
  cache failures; the client retries reads only under the general bounded
  connectivity policy and never treats stale cache data as server truth.

## Decision

**Accept `expo-sqlite~57.0.1` for redacted, bounded snapshots and explicit
migrations.** Do not add SQLCipher, a second database wrapper, or a persistence
package in Stage 1. Keep credentials exclusively in SecureStore and validate
the cache contract on real Android builds.
